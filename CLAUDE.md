# Resource Co. — Project Context

Expo (React Native) resource-management game: buy resources → craft goods → sell for cash → reach a target. Managed workflow, JS (no TypeScript).

**Expo has changed recently.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code — don't rely on older training-data patterns for Expo APIs.

## Architecture

- `context/GameContext.js` — the single source of truth for game numbers (starting cash, objective target, resource prices/stock, recipes) and all game state/actions (`buyResources`, `craftGood`, `sellGood`, `resetGame`) via a `useReducer`. Tune game balance here, nowhere else. Also exports `RESOURCE_IDS`/`RECIPE_IDS` (derived once) — import these instead of re-deriving `Object.keys(...)` locally in screens.
  - **Manufacturing is real-time and exclusive.** Each recipe has `craftTimeMs` (bigger/rarer goods take longer: Clothes 10s, Furniture 15s, Cars 30s, Houses 60s) and `maxHeld` (an inventory ceiling — crafting is blocked once you own that many of the good). Calling `craftGood` doesn't instantly produce goods: it deducts inputs and starts `state.manufacturing = { recipeId, startedAt, endsAt }`; a `useEffect` in `GameProvider` fires `CRAFT_COMPLETE` via `setTimeout` once `endsAt` passes, which is what actually credits the goods. Only one batch — of any recipe — can be in progress at a time, and `buyResources`/`craftGood`/`sellGood` all reject while `state.manufacturing` is truthy. Use `isManufacturing` and `craftBlockReason(recipeId)` (`null | 'busy' | 'missing' | 'full'`) from `useGame()` rather than re-deriving this in screens.
- `theme/tokens.js` + `context/ThemeContext.js` — the only place colors/spacing/radii/type scale are defined. Every component/screen must consume styling via `useTheme()`, never hardcode a hex color or raw pixel value.
- `context/ToastContext.js` + `components/Toast.js` — queued success/error toast banners. Every game action returns `{ success, message }`; screens call the action then immediately pass the result into `useToast()`.
- `constants/icons.js` — icon registry (`RESOURCE_ICONS`, `GOOD_ICONS`, `TAB_ICONS`, `MISC_ICONS`) mapping ids to `{ Component, name }` from `@expo/vector-icons`. Every place an item's icon appears pulls from here so it stays visually consistent. Verify any new glyph name actually exists in the installed glyph maps (`node_modules/@expo/vector-icons/build/vendor/react-native-vector-icons/glyphmaps/*.json`) before using it.
- `components/` — shared primitives (`Button`, `Card`, `Row`, `Badge`, `Stepper`, `ProgressBar`, `EmptyState`, `ScreenContainer`, `ScreenHeader`, `CashDisplay`, `ConfettiBurst`, `HowToPlayModal`, `ManufacturingBanner`) plus `useBevelPress.js` (shared "physical piece" press animation used by `Button`/`Stepper`) and `useCountdown.js` (interval-based ms-remaining hook used by `ManufacturingBanner` and `ProductionScreen`'s active recipe card — same rAF-avoidance reasoning as `CashDisplay`, see Known gotchas). `ManufacturingBanner` is mounted once in `App.js` above `RootTabNavigator`, not per-screen, so the countdown stays visible across tab switches.
- `utils/time.js` — `formatCountdown(ms)`, the only place that turns milliseconds into a `"45s"` / `"1:05"` string; reuse it rather than formatting durations inline.
- `screens/` — the 6 tabs: Home, Market, Production, Inventory, Objective, Results. `MarketScreen` is the one screen that doesn't use `ScreenContainer` (it needs a sticky footer that `ScreenContainer`'s scroll wrapper doesn't support) — it uses the shared `ScreenHeader` component directly instead, to avoid duplicating header markup.
- `navigation/RootTabNavigator.js` — bottom tabs, all 6 always visible (including Results, which shows an "in progress" vs "won" state rather than being conditionally hidden). Mounted as the `"InRace"` screen inside `navigation/RootStackNavigator.js` (see Multiplayer below) — unmodified by multiplayer, still works standalone for Solo mode.

## Multiplayer (Ably)

- `navigation/RootStackNavigator.js` is now the actual app root (swapped in for `RootTabNavigator` in `App.js`): `ModeSelect → RoomSetup → Lobby → InRace` (the existing tab navigator). Solo mode skips straight from `ModeSelect` to `InRace` and never touches any of the below.
- `context/RoomContext.js` (`RoomProvider`/`useRoom()`) is the entire multiplayer layer, and it is **strictly additive** — it only ever reads `useGame()`'s `cash`/`hasWon` to broadcast them; it never dispatches into `GameContext`. Solo mode has zero dependency on Ably or this file's code paths actually running.
  - **Economy model**: each player runs their own complete, independent copy of the single-player game. The room is a live leaderboard/race, not a shared wallet or shared resource pool — reach `OBJECTIVE_TARGET` first to win the race.
  - **Authority model**: no shared backend simulates anyone's game. A tiny serverless function (`server/api/ably-token.js`) mints Ably tokens scoped to `room:<code>` — that's the only place the real Ably API key exists. The client never sees it.
  - Host-ness (`hostId`/`isHost`) is *derived*, not assigned: whoever has been continuously present in the room's Ably Presence set the longest is the host. This self-heals automatically if the host disconnects — no explicit handoff message needed.
  - Who won the race is also derived, not host-arbitrated: Ably guarantees every subscriber sees channel messages in the same order, so every client independently treats the first `player_won` message in that order as canonical.
  - `roomPaused` is derived from comparing the `expectedIds` roster captured at race start (via a host-published `race_start` message) against live Presence — not a message that has to be kept in sync.
  - Trust model, deliberately accepted: there is no server-side validation of any player's self-reported `cash`/`hasWon`. A tampered client could lie. Fine for a casual game among friends; would need a server-authoritative economy to fix, which was explicitly ruled out.
- `components/MultiplayerLeaderboard.js` — persistent live-standings overlay, same "mount once in `App.js`" pattern as `ManufacturingBanner`. Both now render as plain (non-absolutely-positioned) children inside a single positioned stack in `App.js`'s `AppNavigation`, so they don't render on top of each other when both are visible at once.
- `screens/MarketScreen.js`, `screens/ProductionScreen.js`, `screens/ObjectiveScreen.js` each add a `roomPaused`/`raceEnded` check from `useRoom()` alongside their existing `isManufacturing` gate. `screens/ResultsScreen.js` branches on `useRoom()`'s `raceEnded`/`winnerId` in addition to `state.hasWon`, since in a room the race can end because *someone else* won.
- `utils/playerIdentity.js` / `utils/roomCode.js` — persisted player id + display name (AsyncStorage) and room code generation/validation.
- **Setup required before this is testable**: an Ably account + API key (set as `ABLY_API_KEY` in the token server's hosting env, never in the Expo app), the `server/` folder deployed somewhere (Vercel recommended — see `server/.env.example`), and `EXPO_PUBLIC_TOKEN_ENDPOINT_URL` set in the Expo app's `.env` pointing at the deployed function. Without that env var, `createRoom`/`joinRoom` fail gracefully with a "multiplayer isn't set up" message rather than crashing.

## Known gotchas

- **Don't drive UI-visible animations with `requestAnimationFrame` on a component that can be off-screen.** `CashDisplay.js`'s cash count-up is deliberately `setInterval`-based, not `rAF`-based — React Navigation keeps inactive tab screens mounted-but-hidden, and browsers/RN don't reliably run `rAF` callbacks for content that isn't currently being painted, which silently stalled the animation on the Home tab while another tab was active.
- Design palette is intentionally small (3 brand hues + neutrals, in both light/dark variants) — don't introduce new ad-hoc colors outside `theme/tokens.js`.
